基金数据问答系统 - 检索流程图

1
用户输入问题
用户在网页/命令行输入自然语言问题
例如: "基金000006的名称是什么"
↓
2
问题分类
判断问题是简单查询还是复杂查询，决定用哪个模型
简单: "基金000006的名称是什么" → DeepSeek 复杂: "2021年涨跌幅最大的股票" → DeepSeek
↓
3
构建Prompt
把数据库表结构 + 用户问题 组合成提示词发给LLM
System Prompt: "你是基金数据SQL专家。数据库有10张表..." [数据库Schema + 关联关系 + 规则] User Prompt: "问题: 基金000006的名称是什么? SQL:"
↓
4
LLM生成SQL（DeepSeek API）
DeepSeek理解问题后，生成对应的SQL查询语句
输入: "基金000006的名称是什么" 输出: SELECT 基金简称 FROM 基金基本信息 WHERE 基金代码='000006'
↓
5
执行SQL查询（SQLite数据库）
在本地SQLite数据库上执行SQL，获取结果（30秒超时）
数据库: 博金杯比赛数据.db 执行: SELECT 基金简称 FROM 基金基本信息 WHERE 基金代码='000006' 结果: [('西部利得量化成长混合A',)]
↓
6
格式化答案
把查询结果格式化为用户可读的答案
单条结果: 直接显示 多条结果: 分点编号显示 1. 基金A | 数量: 100万 2. 基金B | 数量: 80万
↓
7
返回答案给用户
在网页上显示最终答案
答案: 西部利得量化成长混合A
关键点说明：

1. LLM的作用：把自然语言翻译成SQL语句（NL2SQL），不是直接回答问题

2. 答案来源：所有答案都从SQLite数据库查询得到，不是LLM自己生成的

3. 失败重试：如果SQL执行报错，会把错误信息反馈给LLM，让它修正SQL后重试（最多2次）

4. 招股书问题：涉及公司详情、专利、业务模式等问题，数据库里没有，自动跳过

5. 索引优化：数据库加了索引后，大部分查询从十几秒变成零点几秒
